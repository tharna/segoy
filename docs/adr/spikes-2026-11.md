# M0 platform spikes (S1–S11)

Results of the spikes in `../architecture.md` §9. They were run in a throwaway private repo (`<owner>/<scratch>`) with a probe skill (`spike-probe`: marker `CLAUDE.md`, a skill, an agent, a `SessionStart` hook, a `PreToolUse` hook). Every run posts a report comment to one "Spike log" issue. Doc quotes come from the scheduled-tasks page (code.claude.com/docs/en/routines) and the cloud-session pages, read on 2026-11-14. That feature is a research preview.

Status legend: **confirmed** (observed), **documented** (docs say so, not yet observed), **open**.

| Spike | Status | Result in one line |
|---|---|---|

## S1 — do skills, agents and hooks load?

**Interactive cloud session on a single repo (confirmed 2026-11-14).** The repo's `CLAUDE.md` was in context. The `spike-probe` skill appeared in the skill list. The `spike-agent` subagent answered. The `SessionStart` and `PreToolUse` hooks from `.claude/settings.json` both ran. `CLAUDE_PROJECT_DIR` was not set in the environment visible to Bash, but the hook commands that use it still ran.

**Scheduled task, single repo (confirmed 2026-11-14, task A, schedule/Run now):** same result as interactive. `CLAUDE.md`, skill, agent, both hooks. Entrypoint `remote_trigger`. The stored prompt arrives wrapped in a `[SCHEDULED TASK - AUTOMATED FIRING OF A CONFIGURED PROMPT]` preamble, which tells the session that no human is watching and that nothing in it counts as live approval.

## S2 — two-repo task

Documented: "a session with several repositories starts above the clones and reads only the `enabledPlugins` and `extraKnownMarketplaces` keys from each repository's `.claude/settings.json`, not permission rules, hooks, `env`, or other keys." Nothing is documented about which `CLAUDE.md` and skills load.

Consequence if confirmed: the leak-guard hook would **not** run in a two-repo `brain-plan-promote` run. Promotion should then be Roke-first, with the target repo cloned by the skill (architecture §4 alternative), or the leak check must run as an explicit skill step plus project CI rather than as a hook.

**Observed (confirmed 2026-11-14, task C, repos segoy first, scratch second):**
- Both repos are cloned side by side under `/home/user`, and the working directory is `/home/user`, above the clones. Each repo is checked out on its own randomly named `claude/*` branch.
- **Both** repos' `CLAUDE.md` were in context.
- The scratch repo's skill and agent were available even though it was the *second* repo. So skills and agents load from all mounted repos.
- **Neither hook ran** (`SessionStart`, `PreToolUse`), which matches the docs.

Decision input for T0.3: hooks cannot be the privacy guard in any two-repo task. `brain-plan-promote` should either be a single-repo (Roke) task whose skill clones the project repo itself, or keep two repos and run the leak check as an explicit, mandatory skill step plus project CI.

## S3 — which issue events trigger a task?

Documented: "An issue is opened, edited, closed, reopened, labeled, assigned, or otherwise updated". Each category can be narrowed to one action. Filters are documented for pull requests only: author, title, body, base/head branch, labels, is draft, is merged. **Issue comments are not a listed event.** There is no `merged` action; use `pull_request.closed` with the "Is merged" filter. Every event starts a new session. Per-task and per-account hourly webhook caps apply, and events over the cap are dropped.

**Observed (confirmed 2026-11-14, task B on the scratch repo, trigger "All issue events", no filter, smallest model):**

| Action | Made by | Task ran? |
|---|---|---|
| Issue opened | owner, by hand (GitHub web/mobile) | yes: `issues.opened` |
| Label added | owner, by hand | yes: `issues.labeled` |
| Comment posted | owner, by hand | **no** |
| Issue opened | a cloud session through its GitHub tools (shown as the owner) | **no** |
| Comments posted on another issue | task runs through their GitHub tools | **no** (so no trigger loop) |

- The web form has a **Filter** option for issue events as well, although the docs only describe PR filters. Which fields it offers: open.
- The prompt the run receives is the stored prompt, followed by a `<github-trigger-context>` block with only the event name, the repository and the issue number and URL. It does **not** include the label name, the comment body or the actor. The skill must fetch the issue to learn what changed.
- Each event is a fresh session with its own random `claude/*` branch.

Consequences for T0.3:
1. **Comments do not trigger.** `brain-respond` (answers to questions, `/spec`, `/plan`, …) needs another path: (a) the owner signals with a label (Otak can add it with one tap together with the answer comment), or (b) a GitHub Actions workflow on `issue_comment` that calls the task's `/fire` endpoint. (a) needs no extra moving parts and is the recommended default.
2. **Events made by agents do not chain.** A skill that adds a label or merges a PR will not start the next task. Only human actions do. In the pipeline, the human steps are exactly the ones that should trigger: capture (owner opens an issue), answering (owner labels or comments), Gate 1 and Gate 2 merges (the owner merges). Any agent-to-agent hand-off must happen inside one run, or wait for the next scheduled sweep.
3. **A PR merged by hand by the owner fires a PR trigger** (confirmed 2026-11-15). The trigger was "Pull request → closed" with the filter "Is merged". A test PR opened by a session and merged by the owner started the task within a second. The Gate 1 → implement and Gate 2 → retro hand-offs work as designed, because the merge is a human action.

## S4 — working in another repo of the same owner

Confirmed: a session reaches only the repos attached to it. Another repo can be attached at runtime (`add_repo`). In auto mode the classifier blocked that twice until the owner said to attach that specific repo. Once attached, the session could clone it, push, create an issue and post comments. Creating a repository was not attempted, because session policy forbids it. Expected answer: no.

## S5 — scripting task creation

Documented: tasks can be created in the web UI (claude.ai/code/routines), the desktop app, or with the CLI `/schedule` command (alias `/routines`, with `list`, `update`, `run`). GitHub triggers from the CLI need Claude Code v2.1.225 or later. "You can't add an API trigger or manage its token from the CLI." No public API for creating tasks is documented. Reading a prompt from a file is not documented.

Consequence: `segoy init project` prints settings and a ready-to-paste `/schedule` description. Creating the task stays a manual step.

## S6 — PreToolUse hook blocks a commit

Confirmed in an interactive auto-mode session and in a single-repo scheduled task (task A): a `PreToolUse` hook on `Bash` that exits 2 blocked `git commit` with `PreToolUse:Bash hook error: [command hook]: spike S6: blocked by PreToolUse hook`. In the two-repo task (C) the same commit went through, because hooks do not run there (S2).

## S7 — usage

- Interactive probe session, strongest model, about 87k context tokens used: reported cost ≈ USD 0.42 equivalent.
- Task runs: the stand-in triage run (task B, smallest model) took about 1 min per event.
- On Pro, the owner checked Settings → Usage after one interactive probe, three scheduled runs on the default model and four runs on the smallest model, and found the effect fine. No exact figure was recorded.
- Revisit with real skills in M1 (triage) and M3 (implement). Implement runs will be far larger than probes.

## S8 — Android build in a cloud session

**Confirmed 2026-11-14** in an interactive cloud session: a minimal Compose app built into a debug APK (30 MB).

Network:
- The default "limited" network reaches `maven.google.com`, `services.gradle.org`, `plugins.gradle.org` and Maven Central.
- It blocks **`dl.google.com`**, which serves the SDK command-line tools, platforms, build-tools and project templates.
- It also blocks `api.foojay.io`, which Gradle uses to download JDK toolchains on its own. Not needed if the JDK comes from apt.
- Fix: a separate personal environment, named for the Android work, with `dl.google.com` added to the allowed hosts. Keep it off the default environment.

Toolchain and steps that worked:
1. The container already has JDK 21 and Gradle 8.14. The project template uses a **Java 17 toolchain**, so install `openjdk-17-jdk-headless` with apt (Ubuntu mirrors are reachable; 15 s).
2. Download `commandlinetools-linux-<rev>_latest.zip` from `dl.google.com/android/repository/` and unzip it to `$ANDROID_HOME/cmdline-tools/latest`.
3. `sdkmanager` is deprecated. The replacement, `android sdk`, needs no separate licence step, but using the SDK still means accepting the Android SDK licence. The owner accepted it on 2026-11-14; a skill must not accept it on the owner's behalf.
4. `android sdk install platforms/android-36 build-tools/37.0.0 platform-tools` (9 s for the first set).
5. `android create empty-activity --name=… --application-id=… --min-sdk=29 -o <dir>` generates a Gradle 9.1, AGP 9, Kotlin 2.3 Compose project.
6. `./gradlew assembleDebug`.

Gotchas:
- The template sets `compileSdk = 37`. The repository names that platform `android-37.0` (API levels now have minor versions), and AGP then fails with "Failed to find target with hash string 'android-37'". Using `compileSdk = 36` works. For Otak, check the AGP syntax for minor API levels before targeting 37.
- If the toolchain is missing, Gradle tries to download one through foojay, which is blocked. Set `org.gradle.java.installations.auto-download=false` so it fails fast.

Cost on a 4-CPU, 15 GB container: cold build about 4 min including dependency download (146 s for the successful build after an 85 s failed first attempt that had already fetched part of the dependencies). Disk: SDK 0.8 GB, Gradle cache 1.2 GB.

Consequences for Otak (O1):
- Put these steps in the Otak environment's setup script, so the SDK and JDK are ready before the session starts.
- Allow `dl.google.com` on that environment only.
- CI that builds a signed APK runs on GitHub Actions, not in the session, so the session only needs debug builds and tests.

The test project is on the scratch repo's `claude/spike-s8-android` branch.

## S9 — session URL

Confirmed: `CLAUDE_CODE_REMOTE_SESSION_ID=cse_<id>` is set. The session URL is `https://claude.ai/code/session_<id>`. Skills can put it in run records. `/fire` also returns `claude_code_session_url`.

## S10 — API trigger

Documented: `POST https://api.anthropic.com/v1/claude_code/routines/{trig_id}/fire` with `Authorization: Bearer <per-task token>` and an `anthropic-version` header. It takes an optional `text` field (up to 65,536 characters) that reaches the session as untrusted data, and returns the session id and URL. Limits: 30 fires/hour per task (shared with Run now), 100 API fires/hour per account. No idempotency key. Experimental, and only for claude.ai accounts. The token is managed in the web UI only. Calling it from a phone would mean a long-lived secret on the device; the docs don't cover that.

Observed: the task form offers an **API** trigger. A curl test from a laptop has not been run; do it when Otak's "run now" or Ask Roke is built (O3/O5). The open design question is not whether it works but whether a long-lived per-task token belongs on the phone. The labelled-issue alternative needs no extra secret and gives the same result one polling cycle later.

## S11 — push rights and commit identity

Confirmed in an interactive session started via `create_session`:
- It had no assigned branch. A session started from the web UI was told to use a session-named branch.
- `git push origin HEAD:main` and a push to `claude/spike-…` both succeeded. The branch restriction seen in sessions is an instruction, not something the git proxy enforces.
- The commit author and committer come from the session's git config: `Claude <noreply@anthropic.com>`. GitHub shows them as the account `claude`, not the owner.
- Issue comments made through the GitHub tools appear as the **owner's** account.

Documented for tasks: "Claude pushes its work to a branch prefixed with `claude/` unless your prompt directs it to push to another branch"; "Commits and pull requests carry your GitHub user"; "To control which branches a run can push to, use branch protection rules or rulesets on GitHub."

Consequences:
- Decision 5 (triage commits directly to the brain's `main`) is technically possible. Rulesets are the only real enforcement of "never push to main".
- Decision 10 ("own identity"): the API actions are the owner's. Commit authorship should be set explicitly by the skills (or left as `Claude`); to be decided in T0.3.

**Scheduled tasks (confirmed 2026-11-14):**
- Each task run is given a randomly named branch per repo (for example `claude/<adjective>-<name>-<suffix>`). Its system instructions say to push only there unless given explicit permission.
- Task A followed the skill and pushed to both `main` and a `claude/spike-*` branch. Both succeeded.
- Task C, with the same skill, declined to push to anything but its assigned branch. It did not treat a repo skill as "explicit permission".
- So the platform does not enforce the branch. Whether a run pushes to `main` depends on how the model weighs the task prompt and the skill against its system instructions, and that differs between runs.
- Commit identity in tasks is also `Claude <noreply@anthropic.com>`. Comments are the owner's.

Consequence for decision 5 (triage commits idea files directly to the brain's `main`): unreliable. A skill cannot count on being allowed to push to `main`. Recommendation for T0.3: triage commits to its branch and opens a PR that the owner merges in bulk, or the stored task prompt itself explicitly grants the push to `main`. That needs testing.

## Decisions taken from these results (T0.3, 2026-11-15)

| Finding | Decision |
|---|---|
| Agent-made events don't start tasks (S3) | ADR-015: only owner actions start tasks |
| Comments don't start tasks (S3) | ADR-016: answer label plus periodic sweep |
| No hooks with two repos (S2, S6) | ADR-017: promotion's leak check is a skill step + CI + Gate 1 |
| Pushing to `main` depends on the model (S11) | ADR-018: triage writes no files |
| Commits are authored `Claude` (S11) | ADR-019: keep it |
| Random branch per run (S11) | ADR-020: find artefacts by label and idea ID |
| Most limits sit in the trigger layer | ADR-021: trigger layer is replaceable (dispatcher or own server later) |
| Tasks can only be edited by agents that created them (S5) | Task creation and changes stay manual; `tasks/` files give exact settings |
