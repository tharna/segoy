# M0 platform spikes (S1–S11)

Results of the spikes in `../architecture.md` §9. They were run in a throwaway private repo (`<owner>/<scratch>`) with a probe skill (`spike-probe`: marker `CLAUDE.md`, a skill, an agent, a `SessionStart` hook, a `PreToolUse` hook). Every run posts a report comment to one "Spike log" issue. Doc quotes come from the scheduled-tasks page (code.claude.com/docs/en/routines) and the cloud-session pages, read on 2026-11-14. That feature is a research preview.

## S1 — do skills, agents and hooks load?

**Interactive cloud session on a single repo (confirmed 2026-11-14).** The repo's `CLAUDE.md` was in context. The `spike-probe` skill appeared in the skill list. The `spike-agent` subagent answered. The `SessionStart` and `PreToolUse` hooks from `.claude/settings.json` both ran. `CLAUDE_PROJECT_DIR` was not set in the environment visible to Bash, but the hook commands that use it still ran.

**Scheduled task:** open (task A).

## S2 — two-repo task

Documented: "a session with several repositories starts above the clones and reads only the `enabledPlugins` and `extraKnownMarketplaces` keys from each repository's `.claude/settings.json`, not permission rules, hooks, `env`, or other keys." Nothing is documented about which `CLAUDE.md` and skills load.

Consequence if confirmed: the leak-guard hook would **not** run in a two-repo `brain-plan-promote` run. Promotion should then be Roke-first, with the target repo cloned by the skill (architecture §4 alternative), or the leak check must run as an explicit skill step plus project CI rather than as a hook.

Observation: open (task C, repos segoy + scratch).

## S3 — which issue events trigger a task?

Documented: "An issue is opened, edited, closed, reopened, labeled, assigned, or otherwise updated". Each category can be narrowed to one action. Filters are documented for pull requests only: author, title, body, base/head branch, labels, is draft, is merged. **Issue comments are not a listed event.** There is no `merged` action; use `pull_request.closed` with the "Is merged" filter. Every event starts a new session. Per-task and per-account hourly webhook caps apply, and events over the cap are dropped.

Consequence if confirmed: `brain-respond` must use fallback (a) from architecture §4, state changes by label, or (b), an Actions workflow on `issue_comment` that calls the task's `/fire` endpoint.

Observation: open (task B).

## S4 — working in another repo of the same owner

Confirmed: a session reaches only the repos attached to it. Another repo can be attached at runtime (`add_repo`). In auto mode the classifier blocked that twice until the owner said to attach that specific repo. Once attached, the session could clone it, push, create an issue and post comments. Creating a repository was not attempted, because session policy forbids it. Expected answer: no.

## S5 — scripting task creation

Documented: tasks can be created in the web UI (claude.ai/code/routines), the desktop app, or with the CLI `/schedule` command (alias `/routines`, with `list`, `update`, `run`). GitHub triggers from the CLI need Claude Code v2.1.225 or later. "You can't add an API trigger or manage its token from the CLI." No public API for creating tasks is documented. Reading a prompt from a file is not documented.

Consequence: `segoy init project` prints settings and a ready-to-paste `/schedule` description. Creating the task stays a manual step.

## S6 — PreToolUse hook blocks a commit

Confirmed in an interactive auto-mode session: a `PreToolUse` hook on `Bash` that exits 2 blocked `git commit` with `PreToolUse:Bash hook error: [command hook]: spike S6: blocked by PreToolUse hook`. Task run: open (task A). Per S2, hooks do not run in multi-repo sessions.

## S9 — session URL

Confirmed: `CLAUDE_CODE_REMOTE_SESSION_ID=cse_<id>` is set. The session URL is `https://claude.ai/code/session_<id>`. Skills can put it in run records. `/fire` also returns `claude_code_session_url`.

## S10 — API trigger

Documented: `POST https://api.anthropic.com/v1/claude_code/routines/{trig_id}/fire` with `Authorization: Bearer <per-task token>` and an `anthropic-version` header. It takes an optional `text` field (up to 65,536 characters) that reaches the session as untrusted data, and returns the session id and URL. Limits: 30 fires/hour per task (shared with Run now), 100 API fires/hour per account. No idempotency key. Experimental, and only for claude.ai accounts. The token is managed in the web UI only. Calling it from a phone would mean a long-lived secret on the device; the docs don't cover that.

Observation: open (owner checks the UI; curl from a laptop).

## S11 — push rights and commit identity

Confirmed in an interactive session started via `create_session`:
- It had no assigned branch. A session started from the web UI was told to use a session-named branch.
- `git push origin HEAD:main` and a push to `claude/spike-…` both succeeded. The branch restriction seen in sessions is an instruction, not something the git proxy enforces.
- The commit author and committer come from the session's git config: `Claude <noreply@anthropic.com>`. GitHub shows them as the account `claude`, not the owner.
- Issue comments made through the GitHub tools appear as the **owner's** account.

Documented for tasks: "Claude pushes its work to a branch prefixed with `claude/` unless your prompt directs it to push to another branch"; "Commits and pull requests carry your GitHub user"; "To control which branches a run can push to, use branch protection rules or rulesets on GitHub."

Consequences:
- Decision 5 (triage commits directly to the brain's `main`) is technically possible. Rulesets are the only real enforcement of "never push to main".
- Decision 10 ("own identity"): the API actions are the owner's. Commit authorship should be set explicitly by the skills (or left as `Claude`); to be decided in T0.3.

Task run: open (task A).
